# Changelog

Releases of NetBlueprint Forge, newest first. The release number is the skill's `metadata.version` in `skills/netblueprint-forge/SKILL.md`; the renderer carries its own version inside the template. Every merge to `master` that raises the skill version publishes `netblueprint-forge-<version>.zip` on the Releases page with that version's section below as its notes. `node platforms/package.mjs` builds the same archive locally, byte for byte: every entry is stamped with the date in the version's heading here, not with file times, so a version's archive has one sha256 wherever it is built (from the next release on; the two 0.7.0 archives differ only in file times).

## 0.10.0 (2026-11-04)

Skill 0.10.0, renderer 1.10.0. Download: [netblueprint-forge-0.10.0.zip](https://bifrost.digitalprez.com/download/netblueprint-forge/releases/netblueprint-forge-0.10.0.zip), sha256 `25d5b4b426e96abc1ef0ac2a860320a645424f91a0de9c86bee8e764ddbb1371`.

- Kubernetes, AI and OT cards: `references/kubernetes.md` (control plane, node pool, namespace, ingress, service mesh, registry, secrets, workload identity), `references/ai.md` (model endpoint, agent with tools, tool server, vector store, RAG pipeline, training data, with OWASP LLM Top 10 and MITRE ATLAS references) and `references/ot.md` (controller, HMI and SCADA, historian, engineering workstation, OT DMZ and jump host, safety system, vendor remote access, protocol gateway, with IEC 62443 zones, conduits and security levels and ATT&CK for ICS). The model gains zone kinds `cluster` and `namespace`, `security_level` on zones, component types `llm`, `vector-store`, `ai-agent` and `tool-server`, and `attack.atlas[]`; the validator warns when a conduit enters a higher security level through a zone with no appliance.
- Framework crosswalk and coverage: `assets/frameworks/crosswalk.json`, DigitalPrez's working crosswalk from 54 NIST SP 800-53 Rev. 5 controls to ISO/IEC 27001:2022, PCI DSS 4.0, SOC 2, HIPAA Security Rule and NIST CSF 2.0 clauses (clause numbers and short titles only; no CIS mapping by licence; a `frameworks.json` beside a model extends it). `node scripts/coverage.mjs <model.json> --framework <id>` lists which controls and requirements touch which clause, direct or "via crosswalk", with the best control status; `--gaps` lists untouched clauses; `--frameworks` lists the frameworks. The Threat Register gains a Framework Coverage table of the clauses the model cites directly. `tests/check_coverage.mjs` checks the crosswalk and the coverage; CI runs it.

## 0.9.0 (2026-11-04)

Skill 0.9.0, renderer 1.9.0. Download: [netblueprint-forge-0.9.0.zip](https://bifrost.digitalprez.com/download/netblueprint-forge/releases/netblueprint-forge-0.9.0.zip), sha256 `038312a9156b81fc421122f5f5377f9479dd3066eb40ba4cea49e33e779e645f`.

- Threat enumeration by rule: `node scripts/suggest.mjs <model.json>` runs 23 rules (`scripts/rules.mjs`, STRIDE per interaction: an unauthenticated or password-only flow from the Internet, sensitive data in the clear, a boundary crossed without an appliance, an administrative session without strong MFA or a record, a data store reachable from the Internet, sensitive data sent to a third party, a single point of failure, deprecated TLS, a certificate not validated, a credential in plaintext, an end-of-life platform, no patching, standing or shared admin access, administrators without MFA, no hardening baseline, a risky protocol a card said to disable, a required third-party dependency, weak authentication to a data store, IT traffic into OT, Internet requests without a WAF) and lists candidate threats with STRIDE, CWE, ATT&CK, an adversary, a rating and a mitigation; a threat the model already has on the same target is not proposed again; `--apply` writes the rest as suggested threats to confirm or retire; `--rules` lists the rules. `tests/check_suggest.mjs` proves every rule on `tests/fixtures/rules.model.json` and that the examples get at most a handful. `rule` joins the provenance and mitigation sources.
- Component cards: `references/components.md` holds 21 cards for the self-managed world (web server, reverse proxy, application server, API gateway, relational database, cache, message broker, file share, identity provider, directory, VPN gateway, jump host, mail, DNS, CI/CD runner, secrets vault, backup, workstation, SIEM, firewall, WAF) in the cloud-card format, each with its dependencies, exposure questions, proposals and three threats with controls.

## 0.8.0 (2026-11-04)

Skill 0.8.0, renderer 1.9.0. Download: [netblueprint-forge-0.8.0.zip](https://bifrost.digitalprez.com/download/netblueprint-forge/releases/netblueprint-forge-0.8.0.zip), sha256 `e45245bf15db7bd13e28b1629ccba5f90c6486675c48aa5ca49a18ce6cae698f`.

- Dependencies as structure: `depends_on[]` on nodes, components and appliances (identity, directory, DNS, PKI, KMS, secrets, logging, monitoring, time, package registry …) with the provider on the diagram, and a `dependency` flow kind drawn thin and dashed on its own layer. The validator checks the provider exists, that a flow connects the two and that a dependency flow is declared; the Attributes card shows Depends on and Depended on by; the examples record their secrets, logging and directory dependencies.
- Requirements and evidence: `requirements[]` (`REQ-nnnn`, permanent numbers) state what must hold, name the threats they answer, the controls that satisfy them and the framework clauses they serve; an implemented requirement needs a real control. Controls carry `evidence[]`, ATT&CK mitigation ids, D3FEND techniques, ISO 27001 ids and `frameworks[]` clauses. The Threat Register gains a Requirements table; a threat's card lists its requirements. The examples carry requirements and evidence on every verified control.
- `validate --strict` and `settings.policy`: open threats at a band with no planned control on track, missing treatment decisions, overdue controls, verified controls without evidence, requirements without controls, suggested elements, unclassified flows, accepted risks past review. Each failure is an `error: policy:` line with exit 1; the plain validator still only warns. A policy fixture proves the seven rules.
- `custom` metadata on every element, threat, control, requirement, attack path, tab and the meta block, listed in the Attributes card under Custom.
- `normalize.mjs` learns `dependency_kind`, `criticality`, `requirement_kind`, `requirement_status`, `requirement_source` and `evidence_kind`; the model reference documents the new objects.
- The release archive is deterministic: `platforms/package.mjs` stamps every entry with the date of the version's section in this file (`SOURCE_DATE_EPOCH` overrides it) instead of the files' own times, so the same version gives the same bytes and the same sha256 on a developer machine and in CI. `tests/check_package.mjs` builds it twice and reads it back against the skill folder; CI runs it.
- The repository takes bug reports and feature requests through issue forms and declines pull requests; `CONTRIBUTING.md` and `SECURITY.md` say how. The workflows run on the Node 24 generation of the actions and a pinned `ubuntu-24.04` image.

Terms in `THIRD-PARTY-NOTICES.md`.
- Fixed: a document without tabs now shows its attack paths (the red phase in the band, the paths in the Threat Register, the `#path=` deep link). Renderer 1.7.1 dropped them when the model kept `attack_paths` at the top level instead of on a tab.
