# AI cards: models, agents, retrieval and the data behind them

Cards for the parts of an application that uses a language model or another machine learning model, in the same format as the cloud, component and Kubernetes cards. Use one the moment a node is "the model endpoint", "the vector database", "the agent", "the RAG pipeline"; run its questions, propose with `suggested: true` and `suggested_from: "<card id>"`, and pre-fill its threats for the user to confirm. Component types for this world: `llm` (a model endpoint), `vector-store`, `ai-agent` (a workload that plans and calls tools), `tool-server` (an MCP or plugin server the agent calls); a hosted model API is a `saas` node, a self-hosted one a `service` node with an `llm` component.

Sources: the OWASP Top 10 for LLM Applications (2025: LLM01 prompt injection, LLM02 sensitive information disclosure, LLM03 supply chain, LLM04 data and model poisoning, LLM05 improper output handling, LLM06 excessive agency, LLM07 system prompt leakage, LLM08 vector and embedding weaknesses, LLM09 misinformation, LLM10 unbounded consumption; cite as `standards.owasp: ["LLM01:2025"]`), the OWASP Agentic AI threats, MITRE ATLAS (`attack.atlas: ["AML.T0051"]`), the providers' responsible-use guides. `scripts/suggest.mjs` raises the generic cases (a credential in plaintext, data in the clear, a third-party dependency); the cards hold what is specific to models.

## `ai-model-endpoint` — Model endpoint (a hosted model API, or a self-hosted model server)
- **Icon:** `service` (component type `llm`; node type `saas` for a hosted API)
- **What:** Takes prompts, returns completions or embeddings; sees everything the application puts in the context window.
- **Attaches to:** The Internet side for a hosted API (a `saas` node), or a private subnet with GPUs for a self-hosted server; called by the application over HTTPS with an API key or a workload identity.
- **Default exposure:** Hosted: the provider's endpoint, authenticated by an API key that is easy to leak and often shared; self-hosted: an HTTP server with no authentication at all until one is added.
- **Disable unless needed:** **shared-api-key**, **unauthenticated-model-server**, **training-on-your-prompts** (provider data-use opt-in), **unbounded-token-budget**, **logging-of-prompts-with-personal-data**, **model-from-unverified-source**.
- **Depends on:** `secrets` (the API key), `identity` (workload identity where the provider supports it), `logging`, `monitoring` (token spend), `package-registry` or the model hub (weights), `kms`.
- **Ask:** Hosted or self-hosted? Which data goes into prompts (personal, confidential, secrets)? Does the provider train on it, and is a data processing agreement in place? How is the endpoint authenticated and is the key per application and rotated? Is spend capped? Where do the weights come from and are they verified?
- **Propose:** node `saas` ("Model API", provider named) on the Internet side, or node `service` with an `llm` component in a private subnet; a `data` flow from the application with `auth: api-key` or `managed-identity`, `data_classification` set to what the prompts carry; a `dependency` flow to the vault for the key; `depends_on` kind `api` with criticality.
- **Threats:** Sensitive data in prompts disclosed through the provider, its logs or another tenant · Information disclosure · `sensitive-data-exposure` · CWE-200, AML.T0024 · control: data minimisation and redaction before the prompt, a data processing agreement with training opt-out, a private or dedicated deployment for restricted data (LLM02:2025) ‖ Model weights or a hosted model substituted or backdoored · Tampering · `supply-chain` · CWE-494, AML.T0010 · control: weights from a verified source with hashes and signatures, pinned model versions, an evaluation suite that runs on every model change (LLM03:2025) ‖ Unbounded consumption runs up cost or denies service · Denial of service · `resource-exhaustion` · CWE-770, AML.T0029 · control: per-caller token budgets and rate limits, spend alerts, request size limits, timeouts (LLM10:2025).

## `ai-agent` — Agent with tools (a workload that plans, calls tools and acts)
- **Icon:** `service` (component type `ai-agent`)
- **What:** A loop around a model that reads inputs, chooses tools (search, mail, tickets, shell, APIs) and acts with the application's or the user's identity.
- **Attaches to:** The application tier; calls the model endpoint, one or more tool servers, and whatever the tools reach.
- **Default exposure:** The agent's permissions are the union of its tools'; untrusted content (web pages, mail, documents) enters the same context as the user's instructions.
- **Disable unless needed:** **tools-with-write-or-delete-without-confirmation**, **shell-or-code-execution-tool**, **agent-with-standing-admin-rights**, **unbounded-loop-iterations**, **tool-results-trusted-as-instructions**, **browsing-without-allow-list**.
- **Depends on:** the model endpoint (`api`), `tool-server` components, `identity` (the agent's own, scoped), `secrets`, `logging` (every tool call), `monitoring`.
- **Ask:** Which tools can it call, and which of them write, send, pay or delete? Does it act as itself or as the user? Which content does it read that an attacker could author? Is there a human confirmation for consequential actions? Is every tool call logged with its arguments? Is there an iteration and spend limit?
- **Propose:** node `service` with an `ai-agent` component; `data` flows to the model endpoint and to each tool server with their `auth`; `data_tags` on flows that carry user data; a `control` flow from an approval UI when confirmations exist; `profile.elevated_access` describing the agent's identity.
- **Threats:** Indirect prompt injection in a document or page steers the agent into a harmful action · Elevation of privilege · `injection` · CWE-77, AML.T0051 · control: untrusted content isolated from instructions, tool allow-lists per task, human confirmation for consequential actions, output filtering (LLM01:2025, LLM06:2025) ‖ Excessive agency: a tool with broader rights than the task · Elevation of privilege · `privilege-escalation` · CWE-250, AML.T0053 · control: least-privilege tool scopes, the agent acts with a scoped identity, write and delete tools behind confirmation, no shell tool in production (LLM06:2025) ‖ Agent actions cannot be reconstructed after an incident · Repudiation · `insufficient-logging-monitoring` · CWE-778, T1070 · control: every tool call, its arguments and the model's reasoning summary logged with a correlation id, retained, alertable.

## `ai-tool-server` — Tool server (MCP server, plugin, function-calling backend)
- **Icon:** `api` (component type `tool-server`)
- **What:** Exposes actions and data to an agent as tools; the agent's reach is the tool server's reach.
- **Attaches to:** Beside the agent (local process) or as a service it calls over HTTPS; the server calls the real systems with its own credentials.
- **Default exposure:** Often unauthenticated when local; tool descriptions are read by the model and can carry instructions; the server's credentials are shared by every agent that uses it.
- **Disable unless needed:** **unauthenticated-tool-endpoint**, **tool-descriptions-from-untrusted-sources**, **destructive-tools-without-confirmation**, **shared-backend-credentials**, **tools-returning-raw-secrets**.
- **Depends on:** the systems it fronts (`api`, `database`), `secrets`, `identity`, `logging`.
- **Ask:** Who can call the server and how does it authenticate the agent? Does each tool act with the end user's identity or the server's? Which tools are destructive? Where do its tool descriptions come from and are they pinned? Does it filter what it returns?
- **Propose:** `tool-server` component on the agent's host or a `service` node; `data` flows from the agent with their `auth`; `data` flows from the server to the backends with the identity it uses; `depends_on` kind `api` on the agent.
- **Threats:** Malicious or altered tool description injects instructions into every agent that loads it · Tampering · `supply-chain` · CWE-829, AML.T0053 · control: tool servers from a vetted registry, descriptions pinned by version and hash, reviewed on change ‖ Tool server's credentials act for every caller alike · Elevation of privilege · `excessive-trust-or-flat-network` · CWE-250, T1078 · control: per-user or per-agent delegated identity to the backends, scopes per tool, audit per caller ‖ Tool returns secrets or restricted records into the model context · Information disclosure · `sensitive-data-exposure` · CWE-200, AML.T0024 · control: output filtering and redaction in the tool, least-privilege backend access, no raw credential in any tool result (LLM02:2025).

## `ai-vector-store` — Vector store and embeddings (pgvector, Pinecone, Azure AI Search, OpenSearch, Weaviate)
- **Icon:** `database` (component type `vector-store`)
- **What:** Holds embeddings of documents for retrieval; a copy of the documents' meaning, often without the documents' access controls.
- **Attaches to:** The data tier; written by an ingestion pipeline, read by the application at query time.
- **Default exposure:** Private; the findings are one index for every user regardless of their rights, embeddings of restricted documents, and an API key shared by the whole application.
- **Disable unless needed:** **single-index-for-all-tenants**, **embeddings-of-restricted-documents-without-access-metadata**, **shared-api-key**, **plaintext-index-storage**, **unversioned-ingestion**.
- **Depends on:** the embedding model (`api`), `storage` (source documents), `identity`, `kms`, `backup`, `logging`.
- **Ask:** Does retrieval filter by the user's permissions (metadata, per-tenant indexes)? Which documents are embedded and at what classification? How is the store authenticated? Can embeddings be inverted back to text (treat them as the documents)? Who can write to the index?
- **Propose:** node `database` with a `vector-store` component and `data_classification` of the most sensitive document embedded; `data` flows from the application and the ingestion pipeline with their `auth`; a `dependency` flow to the embedding model.
- **Threats:** Retrieval returns chunks the user may not read · Information disclosure · `unauthorized-access` · CWE-285, AML.T0024 · control: access metadata on every chunk, retrieval filtered by the caller's permissions, per-tenant indexes (LLM08:2025) ‖ Poisoned documents enter the index and steer answers · Tampering · `injection` · CWE-20, AML.T0020 · control: trusted ingestion sources only, content review or classifiers before indexing, provenance on every chunk, versioned indexes (LLM04:2025, LLM08:2025) ‖ Index copied or backed up without the documents' controls · Information disclosure · `sensitive-data-exposure` · CWE-312, T1530 · control: encryption at rest with managed keys, index access as restricted as the sources, backups controlled.

## `ai-rag-pipeline` — Retrieval-augmented generation pipeline (ingestion, retrieval, prompt assembly, output handling)
- **Icon:** `service` (component type `process` or `ai-agent` when it acts)
- **What:** The glue: pulls documents in, builds prompts from retrieved chunks and the user's question, sends them to the model, handles the answer.
- **Attaches to:** The application tier; reads the vector store and the document sources, calls the model, returns to the UI or to downstream systems.
- **Default exposure:** Private; the findings are system prompts that hold secrets or policy, answers rendered or executed without checks, and no evaluation of what the pipeline says.
- **Disable unless needed:** **secrets-in-system-prompt**, **model-output-rendered-as-html-or-executed**, **no-output-filtering**, **no-evaluation-suite**, **prompts-logged-with-personal-data**.
- **Depends on:** the model endpoint (`api`), the vector store (`database`), `storage` (sources), `identity`, `logging`, `monitoring`.
- **Ask:** What does the system prompt contain, and would its leak matter? Is model output treated as untrusted data by the UI and downstream code? Is there an evaluation suite with regression tests for safety and accuracy? Are prompts and answers logged, and with which data?
- **Propose:** `process` component on the application host; `data` flows to the model endpoint and the vector store; `data_classification` on the flow to the model matching the retrieved chunks; a control for output encoding and a control for the evaluation suite.
- **Threats:** Model output rendered as HTML or passed to a shell or SQL · Tampering · `improper-input-validation` · CWE-79, AML.T0051 · control: model output treated as untrusted data, encoded on render, parameterised when it reaches a query or a command, allow-listed when it drives an action (LLM05:2025) ‖ System prompt or embedded policy extracted · Information disclosure · `insecure-design` · CWE-200, AML.T0056 · control: nothing secret in the system prompt, authorisation enforced outside the model, prompt leakage tests in the evaluation suite (LLM07:2025) ‖ Confident wrong answers acted on without review · Tampering · `insecure-design` · CWE-1059, AML.T0043 · control: grounding with citations, confidence thresholds and human review for consequential outputs, an evaluation suite run on every change (LLM09:2025).

## `ai-training-data` — Training, fine-tuning and evaluation data (datasets, labels, feedback)
- **Icon:** `storage` (node type `storage`)
- **What:** What the model learned from, or will learn from; the place where a poisoned record becomes a model behaviour.
- **Attaches to:** Object storage or a data lake reachable by the training pipeline; fed from production data, user feedback and public sets.
- **Default exposure:** Private; the findings are production personal data copied into training sets, public datasets pulled without checks, and feedback loops anyone can write to.
- **Disable unless needed:** **production-personal-data-in-training-sets**, **unverified-public-datasets**, **feedback-written-by-anonymous-users**, **training-pipeline-with-broad-storage-rights**.
- **Depends on:** `storage`, `identity`, `kms`, `logging`, `package-registry` (training code and base models).
- **Ask:** What goes into the training set, from where, and is personal data minimised or consented? Are datasets versioned and hashed? Who can write to the feedback store? Is the trained model evaluated for poisoning and bias before release?
- **Propose:** node `storage` ("Training data") with `data_classification` and tags; `data` flows from sources and feedback with their `auth`; a `data` flow to the training pipeline; controls for dataset provenance and pre-release evaluation.
- **Threats:** Poisoned records in the training or feedback data change the model's behaviour · Tampering · `supply-chain` · CWE-1039, AML.T0020 · control: provenance and hashing of every dataset version, write access to feedback limited and reviewed, poisoning and backdoor evaluation before release (LLM04:2025) ‖ Personal data memorised and regurgitated by the model · Information disclosure · `sensitive-data-exposure` · CWE-359, AML.T0024 · control: minimisation and de-identification before training, membership and extraction tests in evaluation, retention limits ‖ Training pipeline identity with broad storage rights · Elevation of privilege · `privilege-escalation` · CWE-269, T1078.004 · control: a scoped identity for the pipeline, read-only on sources, write only to its outputs.
